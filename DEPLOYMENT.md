# Taptapstar — Deployment Guide

This covers what's needed to take this repo from local development to a live Vercel
deployment, and how to hand the project over to the client's own team. For the manual
account-setup steps (Stripe, Neon, etc.), see `../AgentGuide/05_MASTER_BUILD_GUIDE.md`
Step 0 and Step 12.1 — this file is the technical reference, that one is the click-by-click
walkthrough.

## 1. Environment variables

Copy `.env.example` to `.env.local` for local dev, or paste each value into Vercel's
**Project Settings → Environment Variables** (set for both **Production** and **Preview**)
for a real deployment.

| Variable | Where it comes from | Notes |
|---|---|---|
| `DATABASE_URL` | Neon dashboard → Connection string (pooled) | The app's Drizzle client uses this at runtime. |
| `DIRECT_URL` | Neon dashboard → Connection string (direct, unpooled) | Used by `drizzle-kit` for migrations — needs a direct (non-pooled) connection. |
| `AUTH_SECRET` | Generate a fresh one for production: `openssl rand -base64 32` | **Do not reuse the dev value** — a real deployment needs its own secret. |
| `STRIPE_SECRET_KEY` | Stripe Dashboard → Developers → API keys | Use the **live** `sk_live_...` key for production, not the `sk_test_...` key used during development. |
| `STRIPE_WEBHOOK_SECRET` | Stripe Dashboard → Developers → Webhooks → your endpoint → signing secret | **Must be regenerated for the real deployed URL** — see §3 below. The value used during local dev testing (`whsec_test_local_dev_only`) is a throwaway and must never reach production. |
| `STRIPE_PRODUCT_ID` | Stripe Dashboard → Product catalog | Same Product across test/live mode has different IDs — get the **live**-mode Product ID once Stripe is switched to live. |
| `RESEND_API_KEY` | Resend dashboard → API Keys | Verify a real sending domain before go-live (see §4) — the shared `onboarding@resend.dev` sandbox sender used during development can only send to the account owner's own address. |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | Upstash dashboard → your database → REST API | Powers the `/r/[code]` fraud-throttle. |
| `NEXT_PUBLIC_APP_URL` | The real production domain, e.g. `https://taptapstar.com` | Used for email links and Stripe redirect URLs — get this wrong and password-reset/verification links point at the wrong host. |
| `NEXT_PUBLIC_SITE_NAME` | `Taptapstar` | Cosmetic, safe to leave as-is. |
| `ADMIN_INBOX_EMAIL` | A real inbox the client's team actually checks | Currently set to the Resend-sandbox-verified test address during development — **must change** before go-live, and the new address needs to be a verified sender/recipient once a real domain is set up. |
| `CRON_SECRET` | Generate a real random value: `openssl rand -hex 32` | Checked against the `Authorization: Bearer` header Vercel Cron sends when invoking `/api/cron/weekly-summary` — the dev placeholder (`dev_only_cron_secret_change_before_deploy`) must not ship to production. |

## 2. Running migrations against production

Drizzle migrations live in `drizzle/` (generated by `drizzle-kit generate`, already applied to
the current dev database across Steps 2 through 10). To apply them to a fresh production
database:

```bash
# From the project root, with DATABASE_URL/DIRECT_URL pointed at the PRODUCTION database:
npx drizzle-kit migrate
```

This runs every migration file in `drizzle/` in order — it's idempotent (already-applied
migrations are skipped via `drizzle/meta/_journal.json`), so it's safe to run again if
interrupted. **Do not run `drizzle-kit push`** for production — that's a dev-convenience command
that can silently drop columns; `migrate` is the deliberate, versioned path.

## 3. Seeding a real `taptapstar_admin` account for the client's team

`lib/db/seed.ts` is the **dev-only demo seed** (a taptapstar_admin, a sample "Downtown Cafe"
business, sample devices/employees) — do not run it against production; it's gated behind a
`SEED_CONFIRM=yes` environment variable specifically so it can't be run by accident (see the
warning comment at the top of that file).

For the client's own team, create a real admin account directly instead — either:

- **Sign up normally** at `/signup` (creates a `business`-type account with role `owner`), then
  manually promote that user's `role` to `taptapstar_admin` via a one-off SQL statement:
  ```sql
  UPDATE users SET role = 'taptapstar_admin' WHERE email = 'the-client-admin@their-domain.com';
  ```
  (Run this via the Neon SQL editor or `psql`, not through the app — there's no in-app "promote
  to admin" UI, by design, since that's not something one admin should be able to grant another
  from a compromised session.)
- Or write a one-off script following `lib/db/seed.ts`'s pattern (bcrypt-hash a password, insert
  directly into `accounts`/`users` with `role: 'taptapstar_admin'`) if a password needs to be set
  at creation time rather than via the normal signup+reset flow.

## 4. Handing over the repo

Per the client's own confirmed timeline (`04_PROJECT_STATE.md`'s "Environment / accounts status"
section — *"before live and production I provide you all GitHub, Stripe, repo"*), development
happened in the developer's own GitHub repo and Stripe test-mode account. Before go-live:

1. **GitHub**: either transfer this repo's ownership to the client's GitHub organization/account,
   or push it to a new repo the client controls and update Vercel's connected repo accordingly.
2. **Stripe**: the client needs their own Stripe account (or admin access added to the
   developer's) switched to **live mode**, with a real Product created (see §1's
   `STRIPE_PRODUCT_ID` row) and the webhook endpoint (§5 below) pointed at the real production
   URL.
3. **Neon/Resend/Upstash**: these already had real credentials provided directly by the user
   during development (per `04_PROJECT_STATE.md`) — confirm who actually owns/pays for each of
   these three accounts before go-live; transfer ownership if the developer's own account was
   used.
4. **Domain**: the client already owns and has provided access to the production domain (per
   `04_PROJECT_STATE.md`) — point it at the Vercel project via Vercel's Domains settings, and
   update `NEXT_PUBLIC_APP_URL` to match exactly.

## 5. Stripe webhook — real endpoint registration (manual, cannot be automated from a dev session)

The webhook handler (`app/api/billing/webhook/route.ts`) is fully built and tested, but every
test so far has used a manually-constructed signed payload (via `stripe.webhooks
.generateTestHeaderString`) against a throwaway local secret — **no real webhook endpoint has
ever been registered with Stripe**. Before go-live:

1. Stripe Dashboard → Developers → Webhooks → **Add endpoint**.
2. URL: `https://<your-production-domain>/api/billing/webhook`.
3. Select events: `invoice.payment_failed`, `invoice.payment_succeeded`,
   `customer.subscription.deleted`, `invoice.upcoming` (the four this handler processes — see
   the comment at the top of `app/api/billing/webhook/route.ts`).
4. Copy the endpoint's **signing secret** → set as `STRIPE_WEBHOOK_SECRET` in Vercel's
   environment variables (Production).
5. For pre-deploy local testing of the *real* endpoint (optional, beyond what's already been
   done), use the Stripe CLI: `stripe listen --forward-to localhost:<port>/api/billing/webhook`.

## 6. Pre-deploy sweep (done as part of Step 12)

- ✅ Grepped the full source tree for hardcoded API keys/secrets — none found.
- ✅ Confirmed `.env.local` is gitignored (`.gitignore` line 34) and has never been committed
  (`git log --all -- .env.local` is empty).
- ✅ Confirmed `lib/db/seed.ts` has no automatic invocation path anywhere in `package.json`'s
  scripts or `vercel.json` — it only ever runs via a manual `npx tsx lib/db/seed.ts`, and is now
  additionally gated behind `SEED_CONFIRM=yes` as a second, explicit guard against an accidental
  run against production.
- `console.log` calls reviewed: the ones remaining (in `lib/db/seed.ts` and
  `app/api/billing/webhook/route.ts`) are intentional — seed-script progress output for a
  manual dev tool, and operational state-transition logging for a production webhook handler,
  respectively. Neither is leftover debug cruft; both were left in place deliberately rather than
  stripped, since removing the webhook logs would leave zero visibility into real billing state
  changes in production. Recommend routing these through a real logging/observability service
  post-launch rather than raw `console.log`, but that's a genuine future improvement, not a
  pre-deploy blocker.
